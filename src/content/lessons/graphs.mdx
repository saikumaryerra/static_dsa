## Intuition

Almost anything made of things and connections is a **graph**: cities joined by roads, people joined by friendships, web pages joined by links. The things are **vertices** (also called nodes); the connections are **edges**. That is the entire vocabulary, and it is astonishingly general — trees and linked lists are just special, restricted kinds of graphs.

Edges come in flavors. An edge can be **undirected** — a two-way street, friendship, "either can reach the other" — or **directed**, a one-way arrow from one vertex to another (a follows b, but not the reverse). An edge can also carry a **weight**: a number like a distance, a cost, or a capacity. A road network is a weighted graph; who-follows-whom on social media is a directed graph.

The interesting question is not what a graph _is_ but how you **store** one so a program can work with it. Two representations dominate, and picking between them is a classic space-versus-speed trade-off.

## How it works

The visualization builds a small **directed, weighted** graph one piece at a time: first each vertex appears, then each edge is drawn with an arrowhead (its direction) and a weight label. Watch it assemble, then compare the two ways a program could store the very same graph.

**Adjacency list.** Each vertex keeps a list of its neighbors (and edge weights). It stores only edges that actually exist, so it is compact for **sparse** graphs — the common case, where most possible connections are absent. For the graph in the visualizer:

| Vertex | Neighbors (weight) |
| ------ | ------------------ |
| 0      | 1 (4), 2 (1)       |
| 1      | 3 (5)              |
| 2      | 1 (2), 3 (8)       |
| 3      | —                  |

**Adjacency matrix.** A `V × V` grid where cell `[u][v]` records the edge from `u` to `v` (its weight, or blank for none). Checking whether an edge exists is a single **O(1)** lookup, but the grid always uses `V²` space even when almost every cell is empty. The same graph as a matrix (rows are `from`, columns are `to`):

| from \ to | 0   | 1   | 2   | 3   |
| --------- | --- | --- | --- | --- |
| **0**     | ·   | 4   | 1   | ·   |
| **1**     | ·   | ·   | ·   | 5   |
| **2**     | ·   | 2   | ·   | 8   |
| **3**     | ·   | ·   | ·   | ·   |

Notice the matrix is not symmetric — because the graph is directed. For an **undirected** graph you would store each edge in both directions, and the matrix would mirror across its diagonal.

## Complexity

<ComplexityTable complexity={frontmatter.complexity} />

The table above describes an adjacency **list**. Answering "is there an edge from `u` to `v`?" means scanning `u`'s neighbor list: **O(1)** if it is the first neighbor, up to **O(V)** if `u` connects to nearly every other vertex. Space is **O(V + E)** — one entry per vertex plus one per edge — which is small for sparse graphs. An adjacency **matrix** flips the trade: edge lookup is always **O(1)**, but space is **O(V²)** regardless of how few edges exist. Choose the list when the graph is sparse (usually), the matrix when it is dense or you need constant-time edge checks.

## Common pitfalls

<Callout variant="warning">
  For an undirected edge you must store it in *both* directions in an adjacency
  list — add `v` to `u`'s neighbors and `u` to `v`'s. Forgetting the second half
  turns your "undirected" graph into a directed one by accident, and traversals
  will silently miss half their moves.
</Callout>

<Collapsible summary="Directed is not the same as undirected">
  In a directed graph, an edge `u → v` says nothing about `v → u`; they are
  separate edges that may or may not both exist. Treating a directed graph as
  undirected (or vice versa) is one of the most common graph bugs — it changes
  which vertices are reachable from where.
</Collapsible>

<Collapsible summary="List versus matrix: pick for your graph's density">
  A graph with `V` vertices can have up to about `V²` edges. If it has far fewer
  (sparse), an adjacency list saves enormous space. If it is close to fully
  connected (dense), or you constantly ask "does this exact edge exist?", the
  matrix's O(1) lookup and simple `V × V` storage can win.
</Collapsible>

<Collapsible summary="Weights are optional, and default to 1">
  An unweighted graph is just a weighted graph where every edge has weight 1 (or
  no weight at all). Many algorithms — shortest path, minimum spanning tree —
  only make sense once edges carry weights, so it is worth storing them from the
  start even if you do not use them yet.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. A social network has 1,000,000 users, and each follows about 200 others. Adjacency list or matrix — and why?**

<Collapsible summary="Show answer to question 1">
  Adjacency list. The graph is extremely sparse: 1,000,000 × 200 = 200 million
  edges, but a matrix would need 1,000,000² = a trillion cells, almost all
  empty. The list stores only the edges that exist, using O(V + E) space instead
  of O(V²).
</Collapsible>

**2. In the visualizer's graph, is there an edge from vertex 1 to vertex 2? From vertex 2 to vertex 1?**

<Collapsible summary="Show answer to question 2">
  From 1 to 2: no — vertex 1's only out-edge is to 3. From 2 to 1: yes, with
  weight 2. Because the graph is directed, the two directions are independent,
  and here only one of them exists.
</Collapsible>

**3. Why does an undirected graph's adjacency matrix always mirror across its diagonal?**

<Collapsible summary="Show answer to question 3">
  An undirected edge between `u` and `v` means you can go both ways, so both
  cell `[u][v]` and cell `[v][u]` hold the edge. That symmetry across the main
  diagonal is the visual signature of an undirected graph — a directed graph's
  matrix has no such guarantee.
</Collapsible>
