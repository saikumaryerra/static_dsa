## What you'll learn

- Separate the mutable resume position from the append-only history, and store each accordingly.
- Size a write path generated by running streams rather than by people tapping.
- Choose the consistency guarantee this feature needs, and name the anomalies you accept.
- Write a conflict rule that survives two devices and a rewind.

## Intuition

"Watch history" is two entities wearing one name, and merging them is what makes
this feature expensive.

**The position is a cursor; the history is a log** — a split that is generally
accepted industry architecture wherever a hot mutable value sits on top of an
event record. The cursor is one small
mutable record per profile and title — where playback got to, and when. The log is
append-only: this profile started that title, paused, finished. A cursor is
overwritten thousands of times and read once; a log is written once and read by
batch jobs. Store them together and you get a log you update in place, or a cursor
you have to scan for.

The second idea comes from the [requirements estimate](/learn/sd-netflix-requirements/):
**this is a data-plane-shaped write load inside a control-plane feature.** Position
updates are generated by streams that are already running, not by people touching
screens, so the rate is set by concurrency and continues for hours with nobody
doing anything.

The third is about consistency, and the useful question is not "strong or
eventual" but **which anomaly is acceptable**. A resume point a few seconds behind
reality is fine — the player seeks back a little on purpose anyway. A position that
goes _backwards_ after someone has already seen it is not: pause a television at 42
minutes, open a phone, and being offered 12 minutes reads as data loss. That is
read-your-writes and monotonic reads for one profile — the session guarantees
described by Terry and colleagues in 1994 — and it is much weaker than global
strong consistency, because no two profiles ever compare notes.

## How it works

```text
position   key (profile_id, title_id)  ->  position_s, server_ts, session_id, seq
history    key (profile_id, event_ts)  ->  title_id, event, position_s, device

player -- every 30 s --> viewing-state service
                            |-> upsert the position    (fast path, single key)
                            '-> publish an event       (durable path, append-only)
                                     |-> history store, analytics, model training
```

**The write rate, and the knob that controls it.**

```text
Position writes
  7,200,000 average concurrent streams, one update every 30 s
  7,200,000 ÷ 30                =  240,000 writes/s sustained
  peak concurrency ≈ 3 × average
  21,600,000 ÷ 30               ≈  700,000 writes/s at peak

Move the interval to 60 s
  21,600,000 ÷ 60               ≈  350,000 writes/s at peak
  worst-case resume error moves from 30 s to 60 s

Position store size
  300,000,000 profiles with any viewing history
  ~20 unfinished titles retained per profile, older rows expire
  300,000,000 × 20 × 100 B      =  600,000,000,000 B  ≈  600 GB, and flat

History volume
  400,000,000 starts/day × ~5 events per view = 2,000,000,000 events/day
  2,000,000,000 × 100 B         =  200 GB/day  ≈  70 TB/year
```

Read those together. The position store is tiny — a few hundred gigabytes of hot
rows, held at that size by the retention rule — and takes a colossal write rate. A
year of history is 70 TB, more than a hundred times larger, grows forever, and is
written once per event. Nothing about those two descriptions suggests one system.

**Choosing the stores.** Positions go in a partitioned key-value or wide-column
store keyed by profile ([NoSQL databases](/learn/sd-nosql-databases/)), because
every access is by profile, every write is a blind upsert of a single key, and
nothing needs a transaction across keys. The reference ceiling for a relational
primary is a few thousand indexed writes per second; this path needs two orders of
magnitude more, which is a partitioning problem
([replication and sharding](/learn/sd-replication-and-sharding/)) rather than a
tuning one. The history goes to the event stream first and to cheap append-only
storage behind it, where the analytics and training jobs read it in batches.

**Four levers on the write rate**, in the order to reach for them:

1. **Lengthen the interval.** Thirty seconds to sixty halves the load and doubles
   the worst-case resume error. This is the cheapest trade in the design.
2. **Write durably on transitions only.** Pause, seek, stop and finish are the
   moments a person notices; heartbeats between them can take the fast path.
3. **Batch across keys in the service.** A single key is written once per
   heartbeat, so buffering cannot coalesce it — but the service sees updates for
   hundreds of thousands of _different_ keys each second. Buffer a second or two
   and write each partition's worth in one round trip: the same write rate per
   key, far fewer operations. The cost is losing the buffer on a crash.
4. **Let the client hold the truth in-session.** The player knows its own position
   exactly; the server copy exists for the _other_ devices. Sending on transitions
   and at close, rather than on a timer, cuts writes hard.

**Conflicts, and why the obvious rule is wrong.** Two devices can genuinely be
playing one title. Taking the larger position looks safe and breaks on the most
ordinary action there is: a viewer who rewinds five minutes has deliberately made
the position smaller, and a maximum rule silently undoes it. Wall-clock
last-writer-wins is not much better, because the timestamps come from devices whose
clocks disagree.

The workable rule is **server-stamped last-writer-wins within a session**: the
service, not the device, assigns the timestamp; each playback session carries an
id and a sequence number that only increases; a write wins if it has a later server
timestamp, and a write from the same session with a lower sequence number is
dropped as out of order. Simultaneous viewing on two devices is genuinely
ambiguous, and the honest answer is to take the most recently active session.

<Callout variant="note">
  **Playback never waits on this service.** If the viewing-state store is
  unavailable, a title still starts — from the client's own last known position,
  or from the beginning — and the continue-watching row is left off the home
  page rather than blocking it. A feature that shows where you got to must never
  be able to stop you getting there.
</Callout>

## Trade-offs

**Frequency against precision.** The heartbeat interval is the one knob that moves
write cost, durability and user-visible accuracy at the same time, and every choice
on it is defensible as long as the resulting resume error is stated.

**Durability, chosen separately per entity.** A recovery point objective of about
thirty seconds is fine for positions: the loss is invisible or nearly so. The
history is durable, because models, the "watched" marker and every analysis are
built from it — losing an hour of events is a real loss.

**Session guarantees rather than strong consistency.** Per-profile read-your-writes
needs sticky routing and asynchronous replication. Global strong consistency would
add a cross-region round trip to every one of hundreds of thousands of writes per
second, and would make the feature unavailable during a partition
([CAP and PACELC](/learn/sd-consistency-models/)) — to remove an anomaly nobody
experiences.

**Two stores instead of one.** The cost is a second system and a write that fans
out to both. The benefit is that neither store is asked to do the thing it is bad
at, and a history outage cannot slow a resume.

## Common pitfalls

- **Putting positions in the catalogue database.** Tempting because the row is
  small and the join is convenient; it points a sustained flood of writes at the
  store that browsing depends on.
- **Read-modify-write on every heartbeat.** It feels careful, and it doubles the
  operation count and introduces a race that a blind upsert does not have.
- **Trusting device clocks.** Two devices minutes apart will each overwrite the
  other's newer value, and the bug is invisible in testing on one machine.
- **Merging by maximum position.** It looks like a safe monotonic rule and quietly
  breaks rewinding, which is the most common corrective action a viewer takes.
- **Storing every heartbeat as a history event.** Twenty-four billion heartbeats a
  day against two billion real events multiplies the log roughly twelvefold to
  record nothing anybody queries.
- **Blocking playback start on a state read or write.** It turns the least critical
  dependency into a veto over the most critical action.

## Interview notes

Split the entity in your first sentence — "there is a cursor and there is a log,
and they want different stores" — then give the arithmetic. Concurrency divided by
heartbeat interval is a two-second calculation that produces the number the rest of
the answer defends, and few candidates think to do it.

Then name the anomaly you accept and the one you refuse. "A resume point may be a
few seconds stale; it may never move backwards for the profile that set it" is a
complete consistency requirement, and it is more precise than saying "eventually
consistent".

## Key takeaways

- **Position and history are different entities**: a hot mutable cursor and a cold
  append-only log, with different stores, durability and consistency.
- The write rate is **concurrency divided by heartbeat interval** — about 240,000
  per second on average here, and roughly 700,000 at peak.
- **The heartbeat interval is the design's main knob**, trading write cost directly
  against worst-case resume error.
- The guarantee needed is **read-your-writes and monotonic reads per profile**, not
  global strong consistency.
- **Merge by server-stamped session order, never by maximum position**, because
  rewinding is a legitimate way for a position to shrink.

## Practice

Work each one out before opening the answer.

**1. A colleague proposes storing positions as one small row per profile and title in the relational catalogue database, arguing that the row is a few dozen bytes and the data is naturally related to titles.**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  The row really is tiny, and that is not what makes this expensive — the rate
  is. Seven point two million concurrent streams at one update every thirty
  seconds is about 240,000 writes per second sustained and roughly 700,000 at
  peak, against a reference ceiling of a few thousand indexed writes per second
  for a relational primary. Even if the volume were survivable, the placement is
  wrong: it points a continuous write flood at the store that the entire
  browsing experience reads from, so a spike in viewing degrades the catalogue.
  Positions belong in a partitioned key-value store keyed by profile, where
  every access is a single-key blind upsert and capacity is added by adding
  partitions.
</PracticeCheck>

**2. Device A reports position 12:00 for a title and device B reports 41:00 two seconds later. Why is "take the larger value" the wrong merge rule, and what is a better one?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  Because a position is not monotonic. A viewer who rewinds — the most common
  corrective action there is — deliberately makes it smaller, and a maximum rule
  discards that intent every time, so the title keeps jumping forward to a place
  they moved away from. Use ordering by *recency of the write*, stamped by the
  server rather than by the device, so disagreeing device clocks cannot decide
  the outcome: each session carries an id and a sequence number that only
  increases, a later server timestamp wins, and an out-of-order write from the
  same session is dropped. Applied to this case the answer happens to be 41:00,
  because device B wrote later — but for the right reason, and the same rule
  gives 12:00 when B is the one that rewound.
</PracticeCheck>

**3. To remove any chance of a device seeing an old value, the team proposes making the position strongly consistent across all regions.**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  It buys an anomaly nobody experiences at a price the write path cannot pay. To
  be strongly consistent globally, each of hundreds of thousands of writes per
  second would have to coordinate across regions before acknowledging, adding a
  cross-continent round trip of roughly 150 ms to a write that currently
  completes in single-digit milliseconds — and under a network partition the
  feature would have to refuse writes to stay consistent, so pausing a film
  could fail. What the product needs is narrower: one profile must see its own
  last write and must never see the position move backwards. Those are session
  guarantees, and they are delivered by routing a profile's reads and writes to
  one region and replicating asynchronously — cheap, available under partition,
  and sufficient.
</PracticeCheck>
