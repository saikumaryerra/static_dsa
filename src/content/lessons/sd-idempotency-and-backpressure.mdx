## What you'll learn

- Set a timeout as a decision, and propagate a deadline down a call chain.
- Design idempotency into a write using a client-supplied key.
- Retry without amplifying an outage: backoff, jitter, budgets and breakers.
- Apply backpressure with bounded queues and load shedding.

## Intuition

A timeout is the only way a caller learns that a callee is slow, and it tells
you exactly one thing: no answer arrived in time. It does not tell you whether
the work happened. The request may have been lost on the way out, completed with
the response lost on the way back, or still be running. **Every remote call has
three outcomes, not two: success, failure, and unknown** — and the unknown case
is what this lesson is about.

**Retries are load you generate yourself, at the worst possible moment.** A
dependency slows down, so every caller waits longer, times out and sends the
request again — and it receives more traffic precisely when it can handle less.
That loop turns a small degradation into an outage with no external cause.
Idempotency, backoff, circuit breakers and backpressure all exist to stop it
closing.

**Idempotency** is the property that performing an operation more than once has
the same effect as performing it once. You design it in, usually with a key the
client supplies; retries do not hand it to you, and a retry without it is a
second charge on someone's card.

## How it works

Start with the timeout. Choose it from the dependency's latency distribution —
p99 plus a margin, never the average — and always set one explicitly, because
client library defaults sit somewhere between several minutes and never. Then
propagate a _deadline_ instead of a per-hop timeout:

```text
client budget 300 ms
  gateway sets deadline = now + 300 ms
  service A has spent  40 ms → calls B with a 260 ms deadline
  service B has spent 200 ms → calls C with a  60 ms deadline
  C cannot finish in 60 ms   → fails immediately rather than doing
                               work that nobody is waiting for
```

Per-hop timeouts add up; a deadline does not. Without one, the bottom of the
chain keeps burning capacity on a request the top abandoned long ago.

Now make the write safe to repeat. The client generates a key for the logical
operation — once, before the first attempt — and sends the same key on every
retry of it:

```http
POST /v1/payments HTTP/1.1
Host: api.payments.internal
Idempotency-Key: 8f14e45f-ea6a-4c1e-9f7d-2b0b0f6e0a31
Content-Type: application/json

{ "account": "acct_8812", "amount_cents": 4500, "currency": "GBP" }
```

The server side is a small state machine, and its details are where the property
is won or lost:

```text
on a request carrying key K:
  1. begin a transaction
  2. insert (K, fingerprint of the request)
     with a uniqueness constraint on K
  3. if that insert conflicts:
       same fingerprint      → return the response stored against K
       different fingerprint → reject: K was reused for a different operation
  4. perform the effect
  5. store the response against K, and commit
```

When the effect is a **call to somebody else's system**, step 4 cannot join the
transaction at all. The pattern then changes shape: commit the attempt record
first, make the call, and record the outcome afterwards — accepting that a crash
between the two leaves an attempt whose result you must reconcile, rather than
pretending a distributed transaction is available.

Two details carry the weight. The key record and the effect must commit **in the
same transaction** — if the payment commits and the key record does not, a retry
charges the customer twice, the exact failure the mechanism was bought to
prevent. That is also why there is no "still in progress" state to check: an
uncommitted row is invisible to everyone else, so a duplicate arriving mid-flight
does not read a marker, it **blocks on the unique index** until the first attempt
commits and then reads the stored response — holding a connection, for a slow
effect, the whole time. And the fingerprint check catches a key reused for
different content, a bug worth failing loudly. Keys are kept for a bounded window, commonly around 24
hours, trading storage against how late a retry may arrive.

<Callout variant="note">
  **Which operations are already idempotent.** `GET` and `HEAD` are *safe* —
  they have no effect at all. `PUT` and `DELETE` are idempotent by definition:
  setting a resource to a value twice leaves the same value, deleting twice
  leaves the same absence. `POST` is neither, which is why the key goes there. A
  useful move is turning a creating `POST` into a `PUT` to a client-chosen
  identifier: the protocol then supplies the guarantee and you store nothing.
</Callout>

With a safe write, retries become reasonable — under four rules. Retry only
idempotent operations. Retry only failures that could plausibly succeed next
time: timeouts, connection resets, `429` and `503` with `Retry-After` honoured,
never a `400` or `422`, which will fail identically forever. Use exponential
backoff with full jitter — a random sleep between zero and a cap that doubles
each attempt — because without jitter every caller that failed together retries
together. And keep a retry budget: when retries exceed a small share of traffic,
a tenth is a common figure, stop, because the extra load is helping nobody.

The reason those rules are strict is multiplication:

```text
a chain A → B → C, each hop retrying up to 3 times
C sees 3 × 3 = 9 attempts for every 1 request A made
add a fourth hop and it is 27
```

Retry at one layer — usually the outermost one that can do something useful with
the result — and let the others fail fast.

A **circuit breaker** stops the calls entirely. It watches one dependency's
error rate over a window and moves between three states: _closed_ (calls pass),
_open_ (calls fail immediately inside the caller, for a cool-down) and
_half-open_ (a few probes decide whether it closes or opens again). Its real
value is protecting the caller: a hanging dependency drives latency to the
timeout, and by [Little's Law](/learn/sd-latency-and-throughput/) that drains
the caller's threads and connections until it fails too.

**Backpressure** is a signal from an overloaded component that makes its callers
slow down or stop, rather than letting work pile up invisibly. Its mechanism is
the bounded queue: when the queue is full the producer is blocked or rejected,
and that rejection is information. An unbounded queue is the opposite — it
accepts everything and converts overload into unbounded latency, so requests
time out while still holding memory and answers arrive for callers who left. In
practice backpressure means queues and pools bounded on purpose; concurrency
limits rather than rate limits alone, since in-flight count is what latency
tracks; shedding that rejects quickly with `429` or `503` and a `Retry-After`,
cheapest traffic first; and discarding queued work whose deadline has passed.

```text
concurrency limit 100, service time 50 ms → capacity ≈ 2,000 requests/second
arrivals 3,000 requests/second

unbounded queue → backlog grows by 1,000/second; every request's latency
                  grows with it until memory or patience runs out
bounded queue of 200 → 2,000/second served in ≈ 150 ms,
                  1,000/second rejected in ≈ 1 ms with a Retry-After
```

Rejecting a third of the traffic is a bad day. Accepting all of it is an outage
for everyone, including the two thirds you could have served.

## Trade-offs

**Idempotency keys cost a durable write on every mutating request**, plus the
storage window. For a high-volume, low-value write such as a view event,
at-least-once delivery into a consumer that tolerates duplicates is cheaper. And
because a shorter timeout converts slow successes into retried failures, timeout
tuning is downstream of this decision rather than independent of it.

**A circuit breaker sacrifices requests that would have succeeded.** On a
dependency that is only partly degraded, a badly tuned breaker turns a 5% error
rate into a 100% one for the length of the cool-down.

**Shedding sacrifices some users to keep the rest served**, so somebody must
decide the order. Without an explicit priority you shed whoever happened to
arrive during the spike, including the checkout.

## Common pitfalls

- **Retrying a write that is not idempotent.** Tempting because the failure
  looked like a network problem — and it may have been one, after the payment
  succeeded.
- **Minting the idempotency key per attempt, or on the server.** Then every
  retry is a new operation and the mechanism does nothing. The key names the
  _intent_, so the client creates it once and reuses it.
- **Retrying at every layer, without jitter.** Each layer looks locally
  sensible; the product of their attempt counts lands on the service least able
  to take it, all at the same instants.
- **Unbounded queues added "for safety".** They convert a clear, cheap rejection
  into a slow, expensive, mysterious collapse.

## Interview notes

Whenever you propose a retry, say in the same breath how the operation is made
idempotent. That pairing shows you have thought about the unknown outcome rather
than the happy path, and it costs one clause: "the client retries with backoff,
and the write carries an idempotency key so a repeat is a no-op".

Then say what happens under overload, because most designs quietly assume it
never happens. "We shed at the gateway with `429` and a `Retry-After`, dropping
background sync before interactive traffic, and the breaker opens if the payment
service exceeds a 20% error rate" is a design. "It scales horizontally" answers
a different question.

## Key takeaways

- A timeout leaves the outcome **unknown**, which is why retries need
  idempotency and not the other way round.
- Idempotency is **designed in with a client-supplied key**, stored in the same
  transaction as the effect.
- Retries multiply down a chain — **two hops at three attempts is 9× load** — so
  retry at one layer, with jitter and a budget.
- A **circuit breaker protects the caller** from a hanging dependency, by
  failing fast instead of holding connections.
- Backpressure is a **bounded queue plus a fast rejection**; an unbounded queue
  is an outage with extra steps.

## Practice

Work each one out before opening the answer.

**1. A payment request times out after 5 seconds. What do you know about the state of the payment, and what should the client do next?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  You know nothing about it. The request may never have arrived, may have been
  processed with the response lost on the way back, or may still be executing.
  Retrying blindly risks a second charge; giving up risks reporting a failure
  for a payment that succeeded — two wrong answers to the same missing
  information. The fix has to be in place before you need it: the client sends
  an idempotency key on the first attempt and repeats that key, so a duplicate
  returns the original stored response or is told the first attempt is still
  running. Without a key, the only correct move is to query the payment by a
  client-side reference and reconcile.
</PracticeCheck>

**2. Service A calls B, which calls C. Each layer retries up to three times with backoff. C becomes slow. Describe what C experiences, and where the retries should live.**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  Attempts multiply along the chain: three at each of two hops means C sees up
  to nine attempts for every one request A made, all arriving while C is already
  struggling. Backoff spreads them in time but does not reduce the count, so C
  is handed roughly nine times its normal load exactly when its capacity has
  fallen — a retry storm with no external cause. Retries belong at one layer,
  usually the outermost that can act on the outcome, with inner layers failing
  fast. Add a retry budget so they stop once they exceed a small share of
  traffic, and a breaker so A stops calling a dependency that is plainly down.
</PracticeCheck>

**3. A service can complete 2,000 requests per second and 3,000 arrive. Compare what happens with an unbounded queue and with a bounded queue of 200 plus load shedding.**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  With an unbounded queue the backlog grows by 1,000 requests every second and
  never drains while the overload lasts. Latency grows with it, so within
  seconds every request is answered long after its caller timed out: full work
  done for nobody, and eventual failure on memory rather than load. With a
  bounded queue of 200 the wait is capped at roughly 100 ms of queueing plus 50
  ms of service, so 2,000 a second are served correctly and the excess 1,000 are
  rejected in about a millisecond with a `Retry-After`. That is worse for a
  third of the traffic, far better for everyone else, and the only one of the
  two that recovers by itself when arrivals fall.
</PracticeCheck>
