## Intuition

An array is a row of lockers bolted in a fixed block. A **[linked list](/glossary#linked-list)** is the opposite idea: a treasure hunt. Each node is a scrap of paper holding a value _and_ directions to the next scrap — a **[pointer](/glossary#pointer)**. The nodes can live anywhere in memory; what links them is the chain of pointers. You always start from a special pointer called **head**, which points at the first node.

This flips the array's trade-offs. There is no "jump to index 5" — to reach the fifth node you must start at the head and follow the trail, one hop at a time. But once you are holding the right node, inserting or removing a neighbor is trivial: you just rewrite a couple of pointers. No sea of elements has to shift, because the nodes never move — only the arrows between them change.

A **pointer** is simply a reference that says "the next node is over there." When we "reassign a pointer," we change where that arrow points.

## How it works

The visualization draws each node as a box with an arrow (`next`) to the following node; the final node points at `⌀` (null), meaning "end of list." Named carets under the boxes track our pointers.

1. **Traverse** — to reach node `k`, start `curr` at the head and follow `next` `k` times. Each hop is one step, so reaching a deep node is **O(n)**. A `✓` badge marks nodes we have already passed.
2. **Insert after** a node — create a new node, point its `next` at the current node's old `next`, then point the current node's `next` at the new node. Two arrows change; nothing shifts. That is **O(1)**.
3. **Delete** a node — route the _previous_ node's `next` around the doomed node, so the chain skips it. The unlinked node is then freed. Again just one pointer changes: **O(1)**.

## Complexity

Insert and delete are the best case at **O(1)** — _once you already hold the right node_, only a pointer or two change. But reaching that node is the worst case at **O(n)**, because there is no random access; you walk the chain. Each operation itself needs only **O(1)** extra space (a temporary pointer).

</Bench>

## Common pitfalls

<Callout variant="warning">
  Reassign pointers in the **right order**. When inserting, point the new node
  at the rest of the list _before_ you point the previous node at the new one.
  Do it backwards and you lose the reference to the remaining nodes — leaking
  the whole tail of the list.
</Callout>

<Collapsible summary="Losing the head means losing the list">
  The only handle you have on a singly linked list is `head`. If you overwrite
  it without saving the old value, every node becomes unreachable. Keep a
  temporary pointer whenever you move `head`.
</Collapsible>

<Collapsible summary="Deleting the head is a special case">
  To delete a middle node you reroute its predecessor's `next`. But the head has
  no predecessor, so removing it means moving `head` to `head.next` instead.
  Many implementations use a "dummy" node before the head to avoid this special
  case.
</Collapsible>

<Collapsible summary="Pointers cost memory, and cache misses hurt">
  Every node stores an extra pointer, so a linked list uses more memory per
  value than an array. And because nodes can be scattered across memory,
  traversal jumps around instead of streaming through a contiguous block — often
  making it slower in practice than its O(n) label suggests.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. Why can't you reach the 100th node of a linked list as quickly as `arr[99]` in an array?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  A linked list has no addresses to compute — the only way to a node is by
  following `next` pointers from the head. Reaching the 100th node takes 99
  hops, which is O(n), while an array computes the address directly in O(1).
</PracticeCheck>

**2. You are already holding a node and want to insert a value right after it. How many pointers change, and what is the cost?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  Two pointers change: the new node's `next` (set to the current node's old
  next), and the current node's `next` (set to the new node). No elements shift,
  so it is O(1).
</PracticeCheck>

**3. When inserting a new node, why must you set the new node's `next` _before_ updating the previous node's `next`?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  The previous node's `next` is your only link to the rest of the list. If you
  overwrite it first, you lose that reference and cannot attach it to the new
  node. Point the new node at the tail first, then redirect the previous node.
</PracticeCheck>
