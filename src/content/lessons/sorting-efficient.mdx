## Intuition

The O(n²) sorts get slow because every item is compared against nearly every other item. The fast sorts escape that trap with **[divide and conquer](/glossary#divide-and-conquer)**: split the problem into smaller pieces, solve each piece, and stitch the solutions together. Because splitting in half repeatedly reaches a single element in only about `log n` steps, and each level of splitting does `n` work, the total lands at **O(n log n)** — dramatically faster than O(n²) as `n` grows.

**[Merge sort](/glossary#merge-sort)** splits the array down the middle, sorts each half (by the same method, recursively), then **merges** the two sorted halves into one. The clever part is the merge: combining two _already-sorted_ lists is easy — just repeatedly take the smaller of the two front items.

**[Quick sort](/glossary#quick-sort)** takes the opposite tack. It picks a **pivot** value and **[partitions](/glossary#partition)** the array so everything smaller sits to the pivot's left and everything larger to its right. The pivot is now in its final place; it then sorts the two sides recursively. There is no merge step — the ordering happens during the partition.

Both build on **[recursion](/glossary#recursion)**: a problem solved in terms of smaller copies of itself.

## How it works

**Merge sort — split, then merge.** Keep halving the array until each piece has one element (which is trivially sorted). Then merge pairs of pieces back together: walk a finger down each sorted run and always copy the smaller front value into the result. Merging two runs of total length `k` costs `k` comparisons, and there are `log n` levels of merging, so the whole sort is **O(n log n)** — every time, guaranteed. The cost is memory: merging needs a temporary buffer, so merge sort uses **O(n)** extra space.

**Quick sort — partition around a pivot.** Choose a pivot (here, the last element). Sweep a pointer across the range: each value smaller than the pivot is swapped into a growing "smaller" region on the left. Finally, drop the pivot just after that region — now everything left of it is smaller and everything right is larger, so the pivot is **fixed forever**. Recurse on the left and right sides. Quick sort sorts **in place** (only O(log n) stack space) and is usually the fastest in practice, but a bad pivot can make it slow.

## Complexity

<ComplexityTable complexity={frontmatter.complexity} />

Both sorts do `n` work across about `log n` levels, giving **O(n log n)** — merge sort _always_, and quick sort in the best and average cases. Quick sort's **worst case is O(n²)**: if the pivot is repeatedly the smallest or largest value (for example, an already-sorted array with a last-element pivot), the partitions are lopsided and the recursion degenerates into n levels of n work. Real implementations avoid this with a randomized or median-of-three pivot. On space, merge sort needs an **O(n)** buffer to merge, while quick sort sorts in place using only **O(log n)** stack for the recursion.

## Common pitfalls

<Callout variant="warning">
  Quick sort's O(n log n) depends on balanced partitions. With a fixed pivot, an
  already-sorted (or reverse-sorted) input triggers the O(n²) worst case.
  Randomize the pivot, or use median-of-three, before trusting it on real data.
</Callout>

<Collapsible summary="Merge sort's hidden memory cost">
  Merging cannot be done comfortably in place, so merge sort allocates a
  temporary array — O(n) extra space. That is the trade-off for its guaranteed
  O(n log n) and its stability. When memory is tight, quick sort's in-place
  partitioning is the reason it is often preferred.
</Collapsible>

<Collapsible summary="Stability: merge sort keeps ties in order, quick sort may not">
  Merge sort is **stable** when the merge prefers the left run on a tie
  (`left[i] <= right[j]`), so equal values keep their original order. Quick
  sort's long-distance swaps make the standard version **unstable**. Choose merge
  sort when a stable order matters.
</Collapsible>

<Collapsible summary="Why O(n log n) beats O(n²) so decisively">
  For a million items, n² is a trillion operations; n log n is about twenty
  million. That is roughly a 50,000× difference. The gap only widens with size,
  which is why every practical general-purpose sort is O(n log n).
</Collapsible>

Work each one out before opening the answer.

**1. Merge sort is O(n log n) on every input, but quick sort can be O(n²). What causes quick sort's worst case?**

<Collapsible summary="Show answer to question 1">
  A consistently bad pivot that splits the range into sizes 0 and n−1 instead of
  roughly in half. Then there are `n` levels of recursion, each doing `n` work,
  for O(n²). A sorted array with a fixed last-element pivot is the classic
  trigger; randomizing the pivot fixes it.
</Collapsible>

**2. Why is merging two sorted halves cheaper than sorting them from scratch?**

<Collapsible summary="Show answer to question 2">
  Because each half is already ordered, you only need to compare the two front
  elements and take the smaller one, advancing one finger at a time. That is a
  single linear pass — O(k) for total length k — with no need to re-examine
  earlier items.
</Collapsible>

**3. You must sort a huge array but memory is scarce, and stable ordering does not matter. Merge sort or quick sort?**

<Collapsible summary="Show answer to question 3">
  Quick sort. It sorts in place with only O(log n) stack space, whereas merge
  sort needs an O(n) buffer. Since stability is not required, quick sort's
  in-place speed makes it the better fit — just use a randomized pivot.
</Collapsible>
