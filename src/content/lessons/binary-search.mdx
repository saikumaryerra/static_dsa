## Intuition

Think about looking up a word in a paper dictionary. You do not start at page one and read every entry. You flip to the middle, glance at the word there, and decide: is my word before this page or after it? That one glance lets you throw away half the dictionary. Flip to the middle of what is left, decide again, and throw away half of that. In a few flips you have gone from thousands of pages to the single one you need.

**[Binary search](/glossary#binary-search)** is exactly that idea for a **sorted** list. Because the values are in order, checking the middle one tells you which half your target could be in — so you can discard the other half every single time. Halving again and again is astonishingly fast: a sorted list of a million items is found in about twenty checks.

The one rule you must not forget: the list has to be **sorted first**. Without order, the middle value tells you nothing about which side to keep, and the whole trick falls apart.

### The baseline: linear search

Before binary search, there is the obvious way to find something: start at the first item and check each one in turn until you hit the target or run out of items. That is **[linear search](/glossary#linear-search)**. It is dead simple and it works on **any** array — sorted or not — but it has no shortcut: in the worst case it inspects every element, so searching a million items can take a million comparisons. Binary search exists precisely to beat that steady one-at-a-time march, and the price of admission is that the data must already be sorted. Keep both in mind as you read on: linear search trades speed for zero requirements; binary search demands order and repays you with logarithmic speed.

## How it works

Keep track of the slice of the array you are still searching with two markers: **`lo`** (the first index that might hold the target) and **`hi`** (the last index that might). At the start, that slice is the whole array, so `lo` is `0` and `hi` is the last index.

Each round does three things:

1. Look at the **middle** index, `mid = (lo + hi) / 2` (rounded down).
2. Compare `arr[mid]` with the target:
   - If they are **equal**, you are done — the target is at `mid`.
   - If `arr[mid]` is **less than** the target, the target can only be to the right, so move `lo` to `mid + 1` and discard the left half.
   - If `arr[mid]` is **greater than** the target, discard the right half by moving `hi` to `mid - 1`.
3. Repeat with the smaller slice.

If the slice ever becomes empty — `lo` passes `hi` — there is nowhere left to look, so the target is not in the array.

The visualization below makes the shrinking window concrete: watch `lo` and `hi` close in on the answer, and see which half gets discarded after every comparison.

### How linear search compares

Linear search needs none of this bookkeeping. There is no `lo`, `hi`, or `mid`, and no sorted precondition — just a single index walking from `0` to the end, comparing each value with the target and stopping at the first match. The contrast is the whole point: where binary search **discards half** the remaining items per comparison, linear search **eliminates one**. On the sorted array `[1, 3, 5, 7, 9, 11]`, finding `11` takes linear search six comparisons but binary search only three.

## Complexity

<ComplexityTable complexity={frontmatter.complexity} />

The table above is for **binary search**. Every comparison throws away half of the remaining items, so the number of checks grows with the **logarithm** of the array size — doubling the input adds just one more step. That is the `O(log n)` worst and average case. The best case is `O(1)`: the very first middle you check happens to be the target. Only a couple of index variables are needed, so the extra space is `O(1)`.

**Linear search** is the opposite trade: `O(n)` time in the average and worst cases (it may inspect every element), `O(1)` best case (the target is first), and `O(1)` space. Sorting an array first costs `O(n log n)`, so a single search is not worth sorting for — but if you will search the same array many times, sorting once and using binary search repeatedly wins big.

## Common pitfalls

<Callout variant="warning">
  Binary search silently returns wrong answers on an **unsorted** array. If your
  data is not already ordered, sort it first (or use a different search).
</Callout>

<Collapsible summary="Off-by-one errors with lo, hi, and mid">
  The loop condition is `lo <= hi`, not `lo < hi` — with `<`, a target sitting on
  the final one-element window is missed. Likewise the updates must be `mid + 1`
  and `mid - 1`, never plain `mid`. Setting `lo = mid` (without the `+ 1`) can
  leave the window the same size forever, causing an infinite loop.
</Collapsible>

<Collapsible summary="Integer overflow in (lo + hi) / 2">
  In fixed-width integer languages like Java or C, `lo + hi` can overflow for
  very large arrays. Writing `mid = lo + (hi - lo) / 2` computes the same
  midpoint without ever adding two large numbers — that is why the Java sample
  above uses it.
</Collapsible>

<Collapsible summary="Forgetting the sorted precondition">
  Binary search's speed comes entirely from the array being sorted. If you
  cannot guarantee order, a plain linear scan (`O(n)`) is correct where binary
  search is not. Sorting first costs `O(n log n)`, so binary search pays off
  when you search the same array many times.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. How many comparisons does binary search need, at most, to search a sorted array of 1,000 items?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  About 10. Each comparison halves the range, and 2¹⁰ = 1,024, which is just
  over 1,000. In general the worst case is roughly `log₂(n)` comparisons.
</PracticeCheck>

**2. You run binary search for the value 4 on `[1, 3, 5, 7, 9]`. Walk through the windows — what does it return, and why?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  It returns `-1`. First `mid` is index 2 (value 5), which is greater than 4, so
  `hi` drops to 1. Next `mid` is index 0 (value 1), less than 4, so `lo` rises to
  1. Then `mid` is index 1 (value 3), less than 4, so `lo` rises to 2. Now
  `lo (2) > hi (1)` — the window is empty, so 4 is not present.
</PracticeCheck>

**3. Why can't binary search be used on an unsorted array, even if the target is definitely somewhere in it?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Because the middle value no longer tells you which half to keep. In a sorted
  array, `arr[mid] < target` guarantees the target is to the right. Without order
  that guarantee vanishes, so discarding a half could throw away the very element
  you are looking for.
</PracticeCheck>
