## What you'll learn

- State exactly what a Secret gives you that a ConfigMap does not.
- Explain what base64 does, and where a Secret sits unencrypted.
- Create and read a Secret, and know which commands leak its value.

## Intuition

Start from the honest comparison: a Secret is a ConfigMap with a different name
and a handful of different behaviours. Same namespace scoping, same 1 MiB cap,
same map of string keys, same `kubectl apply`. If you expected a vault, this is
the moment to adjust.

**A Secret is a labelled envelope, not a safe.** The label changes how the thing
is handled — who is allowed to ask for it, which commands print it, where the
kubelet puts it on the node — and it changes none of the mathematics. Anyone who
opens the envelope reads the contents.

The label most people trip over is base64. A Secret's `data` values are
base64-encoded, which looks like ciphertext and is not. **Base64 is an encoding:
a reversible transformation with no key**, used here because `data` has to carry
arbitrary bytes — a binary certificate, a key with newlines in it — through
JSON. `base64 -d` is not an attack on a Secret. It is the format.

<Callout variant="warning">
  Without further configuration, the API server writes a Secret into etcd
  exactly as it writes a ConfigMap: unencrypted. Whoever holds an etcd snapshot
  holds every Secret in the cluster. Turning that off is real, well-documented
  work, and it is the subject of [Secret Management in
  Practice](/learn/k8s-secret-management/).
</Callout>

## How it works

You write a Secret with `stringData` and read it back as `data`:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
stringData:
  username: web
  password: p4ssw0rd-2f7a
```

`stringData` is a write-only convenience field. The API server encodes each
value and stores it under `data`, and a later `kubectl get -o yaml` returns
this instead — the same object, in the form it is actually kept:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  password: cDRzc3cwcmQtMmY3YQ==
  username: d2Vi
```

Those two strings decode to `p4ssw0rd-2f7a` and `web`. Nothing was protected;
something was transported.

The imperative form avoids hand-encoding, which is the safer habit:

```bash
kubectl create secret generic db-credentials \
  --from-literal=username=web \
  --from-literal=password=p4ssw0rd-2f7a
kubectl describe secret db-credentials
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
```

`describe` is the one place Kubernetes shows restraint, printing sizes rather
than values:

```text
Name:         db-credentials
Namespace:    default
Labels:       <none>
Annotations:  <none>

Type:  Opaque

Data
====
password:  13 bytes
username:  3 bytes
```

The third command is how you actually read one, and it belongs in your muscle
memory precisely because it demonstrates that the restraint is a courtesy.

**The `type` field is a contract, not a protection.** `Opaque` means "arbitrary
data, no rules". `kubernetes.io/tls` requires the keys `tls.crt` and `tls.key`,
and is what an Ingress expects. `kubernetes.io/dockerconfigjson` is what
`imagePullSecrets` expects. Types make the API server validate the shape, and
tell other controllers what they are looking at.

**What the envelope buys you**, precisely:

- **A separate RBAC resource.** `secrets` is its own resource name, so a Role
  can grant `get` on `configmaps` and stay silent about `secrets`. This is the
  largest practical difference between the two objects, and the reason to use a
  Secret even knowing everything above.
- **Distance from the image and the Pod spec.** The value is not in a layer
  somebody can pull, and not in the manifest under review.
- **Tools that do not print it.** `describe` shows byte counts, and most
  dashboards follow suit.
- **Different handling on the node.** A Secret mounted as a volume is held in a
  memory-backed filesystem rather than written to the node's disk, and the
  kubelet is only sent the Secrets belonging to Pods scheduled to its node.

**What it does not buy you**, equally precisely: encryption anywhere by default;
protection from anyone who can create a Pod in the namespace, since that person
can mount the Secret and print it; protection from `kubectl get -o yaml`; or any
control over what your own application does with the value once it has it.

## Trade-offs

Knowing all of that, still use a Secret. The alternative is a ConfigMap, which
gives up the separate RBAC surface, the node-level handling and the tooling
restraint while giving up nothing else — a strictly worse position held for the
satisfaction of not being fooled.

What it costs is a second habit. A Secret in a manifest is a plaintext value in
a repository whether or not it is base64, so the object you commit and the value
it carries have to be separated by something: encryption before commit, a
generator at deploy time, or an external store that fills the object in. That is
the next-lesson-but-one problem, and pretending base64 solved it is how
credentials end up in Git history.

## Common pitfalls

- **Reading base64 as encryption.** It is tempting because the value stops being
  legible, and legibility is the thing your eyes were checking for. A reviewer
  who skims a diff and sees no password has been told nothing.
- **`echo` adding a newline.** Encoding by hand with `echo 'hunter2' | base64`
  encodes eight bytes, not seven, and the extra newline reaches your application as
  part of the password. Use `printf '%s'`, or let `--from-literal` do it.
- **Committing the manifest.** A Secret is an ordinary object, so the natural
  move is to keep it beside the Deployment in Git. That puts the credential in
  every clone and every commit, permanently.
- **`kubectl apply` on a Secret from a file.** Apply stores the configuration
  you sent in an annotation on the object, which for a Secret means the
  plaintext lands in a second, less obvious place. Create Secrets imperatively
  or with a tool that knows better.
- **Sharing a namespace to share a Secret.** Namespace membership is the
  boundary here: anyone who can run a Pod in the namespace can read every Secret
  in it, regardless of what their RBAC says about `secrets`.

## Key takeaways

- A Secret is **structurally a ConfigMap** — namespaced, capped at 1 MiB, a map
  of strings — with different handling and a different RBAC resource name.
- **Base64 is encoding, not encryption.** `data` is base64 so it can carry
  arbitrary bytes; decoding needs no key and no permission beyond reading the
  object.
- Without an explicit encryption-at-rest configuration, **etcd holds Secrets in
  the clear**, and so does any backup of it.
- What a Secret genuinely gives you is a **separate authorization surface**,
  distance from the image and the manifest, tooling that does not print it, and
  memory-backed delivery to the node.
- **Anyone who can create a Pod in a namespace can read its Secrets.** Namespace
  design is part of your secret design.

## Practice

Work each one out before opening the answer.

**1. A reviewer approves a pull request adding a Secret manifest, saying the password is "encoded so it is fine in Git". What has gone wrong, and what would have to be true for the review to be fine?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  Base64 is a reversible encoding with no key, so the manifest contains the
  password in full — a single `base64 -d` recovers it, and Git will keep that
  commit forever even if the value is deleted later. The encoding fooled the
  reviewer for the only reason it ever fools anyone: it stopped the value
  looking like a password. For the review to be fine, the committed bytes would
  have to be genuinely unreadable without a key the repository does not carry —
  the manifest encrypted before commit, or holding only a reference that a
  controller resolves against an external store at deploy time. Either way the
  fix is that the repository never sees the value, not that it sees it in an
  unfamiliar alphabet.
</PracticeCheck>

**2. A teammate can deploy workloads into the `payments` namespace but has no RBAC permission on `secrets` at all. They obtain the database password anyway. How?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  They never read the Secret through the API, and they do not need to.
  Permission to deploy workloads is permission to create Pods, and a Pod may
  mount any Secret in its own namespace — so a throwaway Pod that mounts
  `db-credentials` and prints the file hands the value over, with the kubelet
  doing the fetching on their behalf. Their own rule on `secrets` was never
  consulted, because the request that retrieved it came from the kubelet serving
  that Pod. The boundary that actually held here was the namespace, which is why
  a credential nobody on a team should see belongs in a namespace that team
  cannot deploy into.
</PracticeCheck>

**3. Why does a Secret have a `type` field at all, given that `Opaque` accepts anything and no type encrypts anything?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Because the type is a contract between the person writing the Secret and the
  controller that will consume it. `kubernetes.io/tls` makes the API server
  require `tls.crt` and `tls.key`, so an Ingress that expects a certificate can
  rely on those keys existing rather than failing at request time with a
  confusing error; `kubernetes.io/dockerconfigjson` does the same for
  `imagePullSecrets`. It is validation and declared intent — the same job
  `apiVersion` and `kind` do one level up — and it was never about
  confidentiality, which no field of the object provides.
</PracticeCheck>
