## Intuition

An **[array](/glossary#array)** is like a row of numbered lockers bolted to a wall. The lockers sit side by side in one continuous block of memory, and each has a fixed **[index](/glossary#index)** — its position, counted from 0. Because the block is contiguous and every slot is the same size, the computer can compute the exact address of locker `i` with a single multiplication and go straight there. It never has to walk past the earlier lockers.

That is the array's superpower and its weakness in one. **Reading any element is instant** — index 0 and index 999 cost exactly the same. But the lockers are bolted in place: to squeeze a new item into the middle, everything after it has to slide over to make room, and to remove an item, everything after it slides back to close the gap. Sliding a lot of elements is slow.

## How it works

Picture the array as boxed cells, each with its index printed underneath. The bracket beneath the row marks the valid index range — from the first index (**lo**) to the last (**hi**).

- **Access index `i`** — the computer jumps directly to that slot using its address. One step, **O(1)**, no matter how large the array is.
- **Insert `value` at index `i`** — first every element from `i` onward must shift one slot to the **right** to open a gap; only then can the value drop in. In the worst case (inserting at the front) all n elements move, so this is **O(n)**.
- **Delete at index `i`** — removing the element leaves a hole, so every later element shifts one slot to the **left** to close it. Again up to n elements move: **O(n)**.

## Common pitfalls

<Callout variant="warning">
  Inserting or deleting near the **front** of a large array is expensive because
  almost every element shifts. If you do that often, a linked list or a deque
  may fit better than a plain array.
</Callout>

<Collapsible summary="Off-by-one and out-of-bounds indices">
  Valid indices run from `0` to `length - 1`. Reading `arr[length]` runs off the
  end — some languages throw, others return garbage or `undefined`. Always check
  that an index is in range before using it.
</Collapsible>

<Collapsible summary="Dynamic arrays hide a resize cost">
  Python lists and JavaScript arrays grow automatically, but under the hood they
  occasionally allocate a bigger block and copy everything over — an O(n) event.
  Averaged over many appends this works out to O(1) each ("amortized"), but a
  single append can occasionally be slow.
</Collapsible>

<Collapsible summary="Shifting must go in the right direction">
  When inserting, copy from the **right end inward** so you never overwrite a
  value before it has moved. When deleting, copy from the **gap outward** (left
  to right). Reverse either loop and you will smear one value across the array.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. Why is reading `arr[500]` no slower than reading `arr[0]`?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  Because the array is contiguous and every slot is the same size, the computer
  finds any element by arithmetic: address = start + index × slot_size. That is
  a single calculation, so every index costs the same — O(1).
</PracticeCheck>

**2. You insert a value at the very beginning of an array of 1,000 elements. Roughly how many elements move?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  All 1,000. Every existing element must shift one slot to the right to open a
  gap at index 0. That is the worst case for insertion, O(n).
</PracticeCheck>

**3. Deleting the last element of an array is cheap, but deleting the first is expensive. Why?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Deleting the last element leaves no gap to close — nothing shifts, so it is
  O(1). Deleting the first forces every remaining element to shift left by one
  to fill the hole, which is O(n).
</PracticeCheck>
