## Intuition

Picture a tournament bracket flipped upside down: the champion sits at the top, and everyone below is someone that player beat. You do not know the exact ordering of the losers, and you do not care — you only need to know who is on top. That is the deal a **[heap](/glossary#heap)** makes.

A **binary heap** is a binary tree with one rule, the **heap property**: every parent **outranks** its children. In a **max-heap** that means every parent is greater than or equal to its children, so the largest value is always at the root. (A **min-heap** flips it: smallest on top.) Unlike a binary search tree, a heap makes no promise about left-versus-right order — it is a much weaker rule, and that weakness is exactly what makes heaps cheap to maintain.

The payoff: the maximum is always sitting at the root, ready in **O(1)**, and adding a new value only has to bubble up one path, in **O(log n)**. That combination is why heaps power **priority queues** and the sorting algorithm heapsort.

## How it works

Two things make a heap efficient. First, it is a **complete binary tree**: every level is full except possibly the last, which fills left to right. Second, that shape lets you store the whole tree in a plain **[array](/glossary#array)** with no pointers at all — the tree is implied by index arithmetic:

- the node at index `i` has children at `2i + 1` and `2i + 2`,
- and its parent is at `(i - 1) / 2` (rounded down).

The visualization shows both views at once — the tree and its backing array — linked by a dashed tether so you can see that a node and its array cell are the same thing.

To **insert** a value:

1. **Append** it at the end of the array — the next open leaf of the complete tree.
2. **Sift up**: compare it with its parent. If it outranks the parent (in a max-heap, if it is larger), **swap** them and repeat from the parent's position.
3. Stop when the parent is already larger or you reach the root. At most `log n` swaps, because that is the height of the tree.

Removing the max works in mirror image (move the last leaf to the root and **sift down**), but insert and sift-up are enough to see the whole idea.

## Complexity

<ComplexityTable complexity={frontmatter.complexity} />

A single insert appends in constant time, then sifts up at most the **height** of a complete tree, which is about `log n` — so insert is **O(log n)**, and the best case is **O(1)** when the new value is already smaller than its parent and no swaps happen. Reading the maximum is always **O(1)**: it is the root. The heap lives inside the array you already have, so a swap-based sift needs only **O(1)** extra space. (Building a heap by inserting `n` values is `O(n log n)`; a bottom-up heapify can do it in `O(n)`, a nice bonus worth knowing.)

## Common pitfalls

<Callout variant="warning">
  A heap is not a sorted array and not a binary search tree. It only guarantees
  that each parent outranks its children — siblings and cousins are unordered.
  Do not expect an in-order walk of a heap to come out sorted; it will not.
</Callout>

<Collapsible summary="Off-by-one in the index formulas">
  With a 0-based array, node `i`'s children are `2i + 1` and `2i + 2`, and its
  parent is `(i - 1) / 2`. Mixing these up with the 1-based versions (`2i`, `2i
  + 1`, `i / 2`) silently links the wrong nodes. Pick one convention and use it
  everywhere.
</Collapsible>

<Collapsible summary="Sift up versus sift down">
  Insert appends at the bottom and sifts **up** toward the root. Removing the
  max moves the last leaf to the root and sifts **down** toward the leaves.
  Using the wrong direction — sifting down after an insert — leaves the heap
  property broken.
</Collapsible>

<Collapsible summary="Completeness is what lets you use an array">
  The array trick only works because a heap is a *complete* tree filled left to
  right, so there are never gaps in the array. If you allowed arbitrary holes,
  the child/parent index math would point at empty cells and the whole scheme
  would fall apart.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. In a max-heap stored as an array, where is the largest value, and where might the smallest be?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  The largest is always at index `0`, the root. The smallest must be a leaf (a
  node with no children), because any parent is greater than or equal to its
  children — but which leaf is not fixed, so you would have to scan the leaves
  to find it.
</PracticeCheck>

**2. You insert `20` into the heap `[15, 9, 12, 5, 8, 3]`. Trace the sift-up.**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  Append `20` at index `6`; its parent is index `2` (value `12`). `20 > 12`, swap,
  now `20` is at index `2` with parent index `0` (value `15`). `20 > 15`, swap,
  now `20` is at the root. Two swaps, and the new maximum has climbed to the top.
</PracticeCheck>

**3. Why is inserting into a heap O(log n) rather than O(n)?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Sift-up only follows the single path from the new leaf up to the root,
  swapping along the way. That path is as long as the tree is tall, and a
  complete tree of `n` nodes has height about `log n` — so at most `log n`
  comparisons and swaps, never a full scan of all `n` elements.
</PracticeCheck>
