## What you'll learn

- List who can read a given Secret today, and by which route.
- Say what encryption at rest protects, and what it leaves untouched.
- Choose between syncing an external store into a Secret and mounting from it
  directly.
- Perform a rotation that ends with the old credential revoked.

## Intuition

The [Secrets](/learn/k8s-secrets/) lesson said a Secret is an envelope rather
than a safe. This one is about what you put around the envelope, and the way in
is to write the list out.

**Secret management is a question about who, not about what.** For one database
password in a default cluster, today, the list of principals who can read it is:

- anyone with `get` or `list` on `secrets` in that namespace;
- anyone who can create a Pod in that namespace, who can mount it and print it;
- root on any node running a Pod that consumes it;
- anyone holding an etcd snapshot, or the disk underneath it;
- anyone with a copy of your Git history, if the manifest went in;
- your own logs, crash dumps and error tracker, if the application is careless.

Four of those six are outside the API server's authorization entirely, which is
why "we tightened RBAC" is a partial answer. Every technique below removes one
line from that list, and none of them removes all six.

## How it works

### Encryption at rest

By default the API server writes a Secret into etcd as stored bytes with no
encryption. You change that with an **EncryptionConfiguration** file placed on
each control-plane host and passed to kube-apiserver with
`--encryption-provider-config`. That file names the resource types to encrypt —
`secrets` at minimum, often `configmaps` as well — and gives each one an
**ordered list of providers**.

The ordering is the part worth understanding. **The first provider in the list
is used to write; every provider in the list is tried on read.** The `identity`
provider means plaintext, so putting `identity` first and a real provider second
means "write in the clear, but still read anything already encrypted" — which is
how a migration is staged in either direction. `aescbc`, `aesgcm` and
`secretbox` keep their key in the configuration file itself, which means the key
lives on the control-plane disk beside the data. The `kms` provider keeps the
key in an external key-management service instead, and is the only option that
does not leave a usable key on that disk.

<Callout variant="warning">
  Turning encryption on does not encrypt what is already there. The API server
  encrypts on write, so every existing Secret stays exactly as it was until
  something rewrites it. Doing that deliberately is one command:
</Callout>

```bash
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
```

That reads every Secret and writes each one back, re-encrypting it under the
current first provider. It is also what you run after changing a key, and it is
the step people skip.

**What this buys you is exactly one line of the list**: the etcd one. A stolen
snapshot, a decommissioned disk, a backup that left the building. It does
nothing about anyone reading through the API server, because the API server
decrypts on read — which covers RBAC, Pod creation and node access alike. Many
managed clusters offer this as a provider-backed option; knowing whether yours
is on is worth five minutes.

### External secret stores

None of what follows is part of Kubernetes. These are ecosystem projects you
install, and they come in two shapes that behave very differently.

**Sync into a Secret.** A controller — the External Secrets Operator is the
common one — authenticates to Vault, or to a cloud provider's secret manager,
reads a value and creates or updates a native Secret from it. Nothing about your
Pod template changes, so every consumer keeps working, and the value still lands
in etcd, so encryption at rest still matters. What you gain is a single source
of truth outside the cluster, with its own audit trail and its own rotation API.

**Mount from the store directly.** The Secrets Store CSI Driver presents values
from an external store as a volume. Nothing becomes a Secret object unless you
ask it to, so the value never reaches etcd at all. The cost is that the store is
now on the Pod-start path: if it is unreachable, your Pods do not start. Only
file injection works this way, which — after the previous lesson — is the shape
you wanted for a credential anyway.

Both shapes cost you a controller to run, upgrade and be paged for, and both
have to authenticate to the store somehow. Solve that with the cloud's workload
identity where you can, because the alternative is a bootstrap credential
sitting in a Kubernetes Secret.

### Rotation you can actually perform

Rotation is three steps, and the third is the one that makes it rotation:

1. Change the value at the source of truth.
2. Make every consumer use the new value.
3. **Revoke the old value.**

Skip the third and you have made a copy, not a rotation — the leaked credential
still works. Step two is the whole of the previous lesson: an environment
variable needs a new container, a mounted file needs the process to re-read, and
neither happens because you edited an object.

The shape that works has an overlap window, because a
[rolling update](/learn/k8s-deployments/) deliberately runs two versions at
once. For that window some Pods hold the old value and some the new, so both
must be valid or the window is an outage.

```bash
# the new value needs a new object, so the name carries a version from here on
kubectl create secret generic db-credentials-v1 \
  --from-literal=username=web \
  --from-literal=password="$NEW_PASSWORD"
# change the Secret name in the Deployment's Pod template, then apply it
kubectl rollout status deployment/web --timeout=120s
kubectl delete secret db-credentials
```

Between the rollout and the delete sits the step no command can do for you:
confirm that nothing is still using the old credential. Ask the database, the
provider or the audit log — the source that knows who authenticated — rather
than the cluster, which only knows what it mounted.

## Trade-offs

**How far to go is a real decision.** A single cluster with encryption at rest
enabled, credentials created imperatively rather than committed, namespaces that
match team boundaries and a rotation somebody has actually rehearsed is a
defensible position, and it needs no extra software.

Adding an external store before you can rotate buys a second system to operate
and does not shorten the list on its own — the value still arrives in a Secret,
or it arrives on a path that can now fail at Pod start. Add it when you need one
source of truth across several clusters, an audit trail the cluster cannot
provide, or a cadence no human will keep to by hand.

## Common pitfalls

- **Enabling encryption and assuming coverage.** The switch is satisfying and it
  only affects writes. Without the rewrite pass, the oldest and most valuable
  Secrets in the cluster are the ones still in the clear.
- **Expecting encryption at rest to stop a cluster user.** It defends the
  storage layer. Everyone in the first three lines of the list reads through the
  API server, which decrypts for them.
- **Calling an update a rotation.** Changing the Secret and restarting the Pods
  feels complete. Until the old credential is revoked at the source, nothing has
  been rotated.
- **Rotating without an overlap.** Revoking first, then rolling, guarantees a
  window where live Pods hold a credential that no longer works — and rolling
  updates are designed to make that window exist.
- **Bootstrapping the store from the cluster it protects.** Storing Vault's own
  credential in a Kubernetes Secret is a tempting shortcut that leaves the whole
  chain resting on the thing you were trying to stop relying on.
- **Committing the manifest anyway.** If Secrets must live in Git, encrypt them
  before commit or keep only a reference — with tools that are, again, ecosystem
  rather than Kubernetes.

## Key takeaways

- Start by **listing who can read the credential**: RBAC on `secrets`, anyone
  who can create a Pod in the namespace, node root, etcd, Git, your own logs.
  Most of that list is outside the API server's authorization.
- Encryption at rest is an **EncryptionConfiguration** file on the control
  plane: first provider writes, all providers are tried on read, `identity`
  means plaintext.
- It applies **only to writes** — rewrite existing Secrets to cover them — and
  it protects **only the storage layer**, never a caller with API access.
- External stores are **ecosystem, not Kubernetes**, and come in two shapes:
  synced into a native Secret, or mounted directly and never stored in etcd.
- **A rotation is not finished until the old credential is revoked**, and it
  needs an overlap window because a rolling update runs both values at once.

## Practice

Work each one out before opening the answer.

**1. Your cluster has had encryption at rest enabled for a year and a security review finds the oldest Secrets stored in the clear in an etcd backup. How is that possible, and what fixes it?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  Encryption happens on write. When the configuration was turned on, the API
  server began encrypting every Secret it wrote from that point forward and left
  the existing ones exactly as they were — an object nobody has touched since is
  still stored the way it was stored a year ago. The fix is to force a rewrite:
  `kubectl get secrets --all-namespaces -o json | kubectl replace -f -` reads
  every Secret and writes it back, so each one is re-encrypted under the current
  first provider. It is the same pass you need after rotating an encryption key,
  and it is worth putting in a runbook rather than trusting to memory, because
  nothing in the cluster reports the discrepancy.
</PracticeCheck>

**2. A team rotates a database password by updating the Secret and running `kubectl rollout restart`, then immediately deletes the old database user. Requests start failing for about a minute. What happened, and what would you change?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  `kubectl rollout restart` starts a rolling update, which by design replaces
  Pods gradually — so for the length of that rollout some Pods were still
  running with the old password injected at their container start, while the old
  database user had already been deleted. Those Pods could no longer
  authenticate, and they were serving traffic the whole time. The change is an
  overlap window: create the new database credential while the old one is still
  valid, roll the workload, confirm from the database's own authentication log
  that nothing is using the old user any more, and only then revoke it.
  Revocation is the last step of a rotation, not the first.
</PracticeCheck>

**3. A colleague argues that the Secrets Store CSI Driver is strictly better than the External Secrets Operator because the value never reaches etcd. Give the strongest case for each.**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  The point about etcd is correct and it is the CSI driver's real advantage:
  nothing becomes a Secret object, so etcd, its backups and the whole `secrets`
  RBAC surface stop being places the value can be read from. The cost is that
  the external store moves onto the Pod-start path — if it is unavailable during
  a node failure or a scale-up, Pods cannot start — and injection is file-only,
  so a workload that reads its credential from an environment variable has to
  change. The operator's case is the opposite trade: the value lands in an
  ordinary Secret, so every existing Pod template, controller and tool keeps
  working unchanged and a store outage does not stop Pods starting, at the price
  of the value existing in etcd where encryption at rest and RBAC are what
  defend it. Neither is strictly better; they place the dependency in different
  places.
</PracticeCheck>
