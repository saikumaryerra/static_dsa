## What you'll learn

- Trace a home-page request and a play request through every component they touch.
- Say what each box is for, and what breaks if you remove it.
- Place the one handoff where the control plane hands work to the data plane.
- Choose what belongs in a gateway and what must never go there.

## Intuition

The [requirements lesson](/learn/sd-netflix-requirements/) split this platform
into a control plane of JSON and a data plane of video bytes. The architecture is
that split drawn twice. The component set below is a teaching design — generally
accepted industry architecture assembled around this module's numbers, never a
claim about anyone's internals.

**The two planes touch in exactly one place.** A control-plane request ends by
handing the client three things: a manifest listing the available renditions, a
set of signed URLs pointing at a content delivery network, and a licence for the
decryption key. From that instant the client talks to caches near it and never to
an application server again. Everything before the handoff is an ordinary
request-response system running at a few thousand user-initiated queries per
second — QPS. The one exception is the viewing-state write path — 240,000 writes
per second, generated by streams rather than taps, with
[its own lesson](/learn/sd-netflix-playback-state/). Everything after the handoff
is bandwidth.

That is why the component list looks conventional and the system does not. A
gateway, some services, a few stores and an event pipeline is what any read-heavy
product has. The unusual part is that the most expensive thing this product does
is not in the service diagram at all.

## How it works

```text
control plane
  client -> edge PoP: TLS, token check, routing, rate limit
              |
              '-> API gateway / aggregation
                    |-> identity + profile service   -> profile store
                    |-> catalogue metadata service   -> metadata cache -> catalogue store
                    |-> search service               -> title + person index
                    |-> discovery service            -> precomputed rows cache
                    |-> playback service             -> entitlement, manifest, licence
                    '-> viewing-state service        -> key-value store
                          |
                          '-> event stream -> analytics, model training

data plane
  client -> CDN edge cache -> regional cache -> origin (object storage)
```

<NetflixArchitecture />

**The edge** terminates TLS, validates the authentication token, applies per-account
rate limits and routes to a healthy region. It is a reverse proxy with a routing
table ([load balancers](/learn/sd-load-balancers/)), and the rule is that it may
reject a request but never decide what one means. Business logic that drifts into
the edge cannot be tested, versioned or rolled back independently.

**The aggregation layer** turns one client call into a page. A television, a phone
and a browser want different numbers of rows, artwork sizes and codec lists, so a
device-shaped endpoint per client class collapses a dozen round trips into one — a
teaching illustration, not a measurement. Netflix's public writing on its
microservice API tier documents that move: per-device endpoints rather than one
generic REST API. The fan-out shape is generally accepted industry architecture
for any read-heavy product.

**The catalogue metadata service** owns titles, seasons, episodes, artwork
references and regional availability. Its user-facing traffic is read-only: the
write path is an ingest pipeline run by the content organisation, not by viewers.
Because the catalogue is small, a full copy fits in a cache tier and the store
behind it can be an ordinary document or relational store
([choosing one](/learn/sd-relational-databases/)) rather than a partitioned
cluster. **Title-and-person search** runs on a small
[inverted index](/learn/sd-search-indexes/) over that same catalogue, rebuilt from
it rather than replicated, and degrades to a prefix match over cached metadata.

**The discovery service** serves the personalised home page by reading rows a
pipeline computed earlier, then applying cheap online adjustments. The ranking
itself belongs to [the next lesson](/learn/sd-netflix-recommendations/); what
matters architecturally is that serving is a cache read, not a model run.

**The playback service** is the one that must not fail. It checks entitlement,
picks the renditions this device can decode, returns the manifest and signed URLs,
and issues the DRM licence. It is deliberately not part of discovery: the two have
different availability targets and different dependencies, and a ranking model
that will not load must never stop a title from starting.

**The viewing-state service** absorbs position updates and writes an event per
playback action into a stream ([event streams](/learn/sd-event-streams/)). That
stream feeds analytics, experiment measurement and the offline training jobs that
rebuild recommendations.

**Object storage** holds mezzanine masters and every encoded rendition
([object storage](/learn/sd-object-storage/)) and acts as origin for the delivery
tier. It is the only store measured in petabytes.

**What each box is for.** The test for a component is what fails without it.

| Component           | What breaks if you remove it                                                                       |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| CDN and edge caches | 90 Tbps peak arrives at origin; delivery becomes physically impossible                             |
| API gateway         | Every client re-implements auth, retry and rate limiting; nowhere to shed load in one change       |
| Metadata cache      | Thousands of home builds per second multiply into database reads of a catalogue that never changes |
| Search index        | Every title lookup becomes a scan of the catalogue, and knowing the name stops helping             |
| Precomputed rows    | Ranking runs inline on the request path, at peak, for every profile                                |
| Separate playback   | A discovery incident becomes a playback incident, and the strictest target is lost                 |
| Viewing-state store | Resume dies — and if it shares the catalogue store, its write rate takes browsing down with it     |
| Event stream        | Recommendations have no training data, and the write path couples to analytics                     |
| Object storage      | There is no origin of truth for renditions, so a cache miss cannot be filled                       |

<Callout variant="note">
  **Read the table as an argument, not an inventory.** A component whose answer
  is "nothing, but it is good practice" is a component to remove, and one whose
  answer is "everything" deserves a second look at its own failure story.
</Callout>

## Trade-offs

**Many services buy isolation and cost tail latency.** Splitting playback from
discovery is what lets one keep four nines while the other keeps three. The bill
arrives at the aggregation layer: a page that fans out to eight services waits for
the slowest of eight, so its p99 is worse than any single service's. Dean and
Barroso's _The Tail at Scale_ (CACM, 2013) is the standard treatment, and the
answers are the same here — hedge slow requests, and make every dependency of the
page optional.

**Device-shaped endpoints buy round trips and cost a contract per client.** A
generic API is one thing to maintain and many calls to make; an endpoint per
device class inverts both. With a decade-old television on the other end, the
round trips are the expensive side.

**A precomputed home page buys latency and costs freshness.** Rows built hours ago
serve in single-digit milliseconds and cannot reflect what the profile watched ten
minutes ago, which is why the online layer re-ranks rather than regenerates.

**Signed URLs buy public cacheability and cost revocation.** Entitlement is checked
once, when the URL is minted, so the bytes behind it are cacheable for everyone.
The price is that a short expiry is the only revocation mechanism there is.

## Common pitfalls

- **Letting two services share one database.** Tempting because it removes an API,
  and it silently couples the availability, the schema and the write budget of two
  systems that were split for a reason.
- **Putting the licence behind the recommendation stack.** Tempting because both
  are "the backend", and it hands the least critical dependency a veto over the
  most critical action.
- **Caching a personalised response at the edge.** The home page is the hottest
  surface and the most personal one; the shell and the artwork cache, the ranked
  rows do not ([CDN caching rules](/learn/sd-cdn/)).
- **Making the gateway a monolith.** Aggregation logic accretes there because it is
  the one place that sees every service — and the result is a component everything
  depends on and nobody dares deploy.
- **Treating analytics as a synchronous dependency.** A playback event that blocks
  on a warehouse write turns a reporting outage into a playback outage.

## Interview notes

Draw the handoff explicitly and name what crosses it: manifest, signed URLs,
licence. Candidates who draw a box labelled "video service" between the client and
the CDN have not yet separated the planes, and interviewers watch for it.

Then defend one split out loud. "Playback is separate from discovery because they
have different availability targets and I do not want a model-loading failure to
stop a title starting" shows that the boxes came from requirements rather than
from a diagram someone remembered.

## Key takeaways

- The control plane and the data plane meet **once**, when playback returns a
  manifest, signed URLs and a licence.
- The **edge may reject a request but must not interpret one**; business logic in a
  gateway cannot be deployed or rolled back on its own.
- **Serving discovery is a cache read**, not a model run; ranking happens earlier
  and offline.
- **Playback is split from discovery on purpose** so the strictest availability
  target does not inherit the loosest dependency.
- Every component earns its place by naming **what breaks without it** — fan-out
  costs tail latency, so a page's optional dependencies must be genuinely optional.

## Practice

Work each one out before opening the answer.

**1. A proposal merges the playback service into the discovery service, arguing that both are read paths for the same client and the merge removes a network hop.**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  The hop is real and worth about a millisecond inside one data centre; the
  coupling costs far more. The two have different availability targets —
  playback start is the four-nines path, discovery is allowed one nine less —
  and merging them means the merged service inherits the stricter target while
  carrying discovery's dependencies: the ranked-row cache, the model artefacts,
  the experiment assignment. Any of those failing now blocks a title from
  starting, which is the outage the split exists to prevent. They also scale
  differently: home builds track people opening the app, playback starts track
  people choosing something. Merge them and one deployment cadence and one
  autoscaling policy have to serve both.
</PracticeCheck>

**2. The home page fans out to eight services and each has a p99 of 40 ms. Why is the page's p99 worse than 40 ms, and what do you do about it?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  Because the page waits for the slowest of the eight. If each call
  independently exceeds 40 ms one time in a hundred, the chance that no call
  does is roughly 0.99 to the eighth power, about 92% — so something like one
  page in twelve is slower than the number every individual service reports.
  This is the tail amplification Dean and Barroso describe in *The Tail at
  Scale* (CACM, 2013). The fixes are structural rather than per-service: make
  dependencies optional so the page renders without a slow row, set per-call
  deadlines that are shorter than the page's own budget, hedge a slow request
  against a second replica, and reduce the fan-out where a call can be
  precomputed instead.
</PracticeCheck>

**3. Why does the event pipeline sit behind the viewing-state service rather than being called directly by the client?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Two reasons, one about trust and one about coupling. A client-written event is
  unauthenticated data about itself, so the server has to validate and enrich it
  anyway — profile, entitlement, title version — and doing that in one place
  means one implementation rather than one per device class. The coupling reason
  matters more at this scale: routing events through the service that already
  handles the position write lets the platform accept the write, acknowledge the
  client, and publish to the stream asynchronously. If the stream is degraded,
  playback and resume keep working and events buffer; if the client published
  directly, a pipeline problem would surface as errors on hundreds of millions
  of devices that cannot be redeployed quickly.
</PracticeCheck>
