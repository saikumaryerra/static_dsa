## Intuition

Imagine a coat-check counter with a row of numbered hooks. When you hand over a coat, the attendant does not search for an empty hook — a quick rule turns your ticket number straight into a hook number, and the coat goes there. Later, the same rule points right back at the hook. No scanning, no guessing: compute the spot, go to the spot.

A **hash table** works exactly like that for data. You have an array of slots called **[buckets](/glossary#bucket)**. A **[hash function](/glossary#hash-function)** takes a key and turns it into a bucket index — for whole-number keys, a simple one is `key % number_of_buckets`. To store a key you hash it and drop it in that bucket; to find it you hash it again and look only in that one bucket. Because you jump straight to the right bucket instead of scanning everything, lookups are on average **O(1)** — constant time, no matter how many keys you have stored.

There is one wrinkle. Two different keys can hash to the **same** bucket — that is a **[collision](/glossary#collision)**. Hash tables are defined by how they handle them, and the simplest way is the one this lesson shows.

## How it works

We handle collisions with **[separate chaining](/glossary#chaining)**: each bucket holds a little list (a chain) of all the keys that hashed to it. The visualization draws the buckets as a vertical column of numbered slots; each bucket's chain grows to the right using the same node-and-arrow picture you saw for linked lists.

1. **Hash** — compute `bucket = key % capacity`. The `▶` caret marks the bucket being probed.
2. **Insert** — append the key to that bucket's chain. If the bucket was empty, the chain has one entry and there was no collision. If it already held a key, the new one is **chained** onto the end — a collision made visible, with a `+` marking the added entry.
3. **Search** — hash the target to a bucket, then **walk the chain**, comparing the target against each stored key until you find a match (`✓`) or reach the end.

The fewer keys share a bucket, the shorter the chains and the faster the lookups. The ratio of keys to buckets — the **load factor** — is the dial that controls this, and the visualization prints it after the inserts.

## Complexity

<ComplexityTable complexity={frontmatter.complexity} />

With a good hash function and enough buckets, keys spread out, chains stay short, and insert and search are on **average O(1)** — you compute the bucket and touch only a handful of entries. The **worst case is O(n)**: if every key collides into one bucket, that bucket becomes a linear list and you are back to scanning all `n` keys. The table stores every key, so space is **O(n)**. Keeping the load factor low (real hash tables grow and rehash once it passes roughly `0.75`) is what keeps you in the fast average case.

## Common pitfalls

<Callout variant="warning">
  A hash table's speed lives and dies by its hash function. A function that
  sends many keys to the same bucket produces long chains and O(n) lookups. Real
  implementations use far better hashing than `key % capacity` and resize the
  bucket array as it fills.
</Callout>

<Collapsible summary="A hash table has no inherent order">
  Because keys are scattered across buckets by their hash, iterating a hash
  table does not visit keys in sorted order — or any predictable order. If you
  need order, use a balanced tree (or sort the keys on the way out).
</Collapsible>

<Collapsible summary="The load factor is the dial that matters">
  Load factor is `keys / buckets`. Low load factor means short chains and fast
  lookups but wasted empty buckets; high load factor saves space but lengthens
  chains. Growing the array and rehashing when the load factor crosses a
  threshold keeps the average O(1).
</Collapsible>

<Collapsible summary="Keys must be hashable and comparable">
  Hashing needs a stable rule for turning a key into an index, and searching a
  chain needs a way to test two keys for equality. If a key's hash can change
  after it is stored (a mutable key), you may never find it again — its bucket
  moved out from under it.
</Collapsible>

## Practice

Work each one out before opening the answer.

**1. With capacity 5, which bucket does key `17` hash to, and which existing key would it collide with in the visualizer's table?**

<PracticeCheck slug={frontmatter.slug} index={1} total={3}>
  `17 % 5 = 2`, so it lands in bucket 2. In the default table bucket 2 is empty,
  so there is no collision — `17` would sit alone in bucket 2.
</PracticeCheck>

**2. Why is a hash-table lookup O(1) on average but O(n) in the worst case?**

<PracticeCheck slug={frontmatter.slug} index={2} total={3}>
  On average, keys spread across buckets, so each bucket's chain is short and
  you compare against only a few keys — constant work. In the worst case every
  key hashes to the same bucket, forming one chain of length `n`, and searching
  it is a linear scan of all `n` keys.
</PracticeCheck>

**3. You insert 8 keys into a table with 4 buckets. What is the load factor, and what does that tell you?**

<PracticeCheck slug={frontmatter.slug} index={3} total={3}>
  Load factor is `8 / 4 = 2.0` — on average two keys per bucket. That is high:
  chains are lengthening and lookups are slowing. A real hash table would have
  grown its bucket array and rehashed before reaching this point.
</PracticeCheck>
